DeepSeek Harness 通俗易懂全解读

一个"一切皆插件"的 AI 智能体运行时——用经营一家公司的方式，讲清楚它是什么、能做什么、怎么运转

1 DeepSeek Harness 是什么？
先打个比方：dsh 就像一家专门为 AI 开的公司。你不是直接对着模型喊话，而是坐进这家公司当老板——公司没有固定部门，谁有本事谁挂牌上岗（一切皆插件）；墙上挂着一本总台账，干过的每件事都先记账（日志即真源）；员工想动公司的东西，得先过门卫查工牌、该签字的找人签字（工具审批）。你交代任务，公司按流程把活干完，每一步都留痕。

DeepSeek Harness（直译是「DeepSeek 脚手架」，命令名叫 dsh）是 DeepSeek AI 开源出来的一套 AI 智能体（agent，指能自己动手干活、不只是陪聊的 AI 程序）运行框架。用大白话说：它不负责「模型聪不聪明」，它负责「活儿怎么干」——把模型、工具、权限、记录这些零件，组装成一个可以上班干活的 AI 员工。

这套东西以 MIT 许可开源，配套一篇论文，编号 arXiv:2608.25512。要特别提醒一句：它现在处于开发者预览阶段，README 开头就明说之后会有破坏兼容性的变更——意思是「接口说变就变，别急着锁死用法」。上手也简单：一条启动命令就能在你自己电脑的 127.0.0.1（就是本机）3080 端口开出一个网页界面；想从源码跑，就先装依赖、再构建、然后启动。

一切皆插件

公司没有固定部门，所有能力都是挂牌小组：摘牌的时候，桌椅（注册留下的东西）会自动带走、恢复原样。这套挂牌制度由 Cordis（一个插件框架）驱动，底层没有特权内核，谁都可以被替换。

事件驱动

部门之间不互相打电话，全靠内部通知系统（事件）沟通：有群发广播、有传阅签字、有排队处理等好几种发通知的方式，后面几节细讲。

日志即真源

公司只有一本总台账：所有事实先记进台账，之后任何报表、任何「刚才发生了什么」，都随时从台账重新算出来，而不是凭记忆说。

2 支持哪些能力？
还是拿公司打比方：dsh 这家公司能自己接单干活、能把活拆给几个分身同时干、干到一半能停下来等你签字、走之前会把台账留得清清楚楚。但它也有边界——它不会替你定「最多干几轮就收工」的规矩（预算得你自己加闸），有的岗位还挂着「试用期」的牌子（实验性功能），分身也不会自动继承总部给的全部权限。

把能力摊开看，dsh 的本事大致分这几类：

组装一门可换装的公司

5 种运行组合随便挑，配置像四层命令一层盖一层，随时能改；所有能力都是插件，注册可逆，摘牌自动还原。

五种发通知的方式

事件（部门间的通知）有五种模式：群发广播、传阅签字且可改笔（不签字就不往下走）、各干各的、排队处理、到某人为止。

会自己转的干活循环

一轮工作里做几件任务，每件任务问一次模型、干一批工具活，失败了还会重试，直到这轮的输入全部处理完。

工具出门有关卡

员工要动公司资产：先查工牌、该审批的找人签字、门卫终审、执行、事后再检查一遍，最后落盘记台账。

多员工协作

可以派分身（subagent，替主员工干活的小同事）干活，可以写编排脚本让模型自己调度，还有一个实验性的团队模式。

账本随身带

会话只增不改地记台账，崩了能补记，随时从台账还原「公司到哪一步了」。

3 DeepSeek Harness 怎么做的？
3.1 整体架构
先用公司打比方：这家公司的架构分四层——大门（5 种入口）→ 人事规章一层层覆盖（4 层配置）→ 服务总台（插件容器）→ 挂牌小组（插件池）。每项能随时换人的能力，都由三样东西凑齐：岗位说明书（Definition，这项能力长什么样的定义）、可任免的任职者（Provider，具体干活的实现）、来用这个岗位的同事（Consumer，调用的一方）——换掉任职者，整项能力就换了人干。（现实里岗位说明书自己也会改版升级，这一点公司类比并不完全贴切。）

对应到 dsh：最上面是 5 种运行组合（profile，一次选好一组功能的搭配套餐）当入口；往下是 4 层配置组装——运行组合包、profile 补丁文件、home 级补丁、命令行临时覆盖，后一道盖前一道，还可以用命令把最终的配置树整棵打印出来看；再往下是插件容器（ctx，大家可以理解为服务总台）：插件是实现了服务（Service，就是上面说的「岗位」）的对象，谁需要谁就用 inject 声明依赖（相当于说「我这个岗位要用到那几张桌子」），彼此之间用类型化事件（带明确含义的内部通知）沟通；最底下是插件池，插件有三个来源：内置的核心包、运行组合带进来的、补丁追加或替换的。

核心包一共 7 个，其中主干六包是会话（session）、系统提示词（system-prompt）、工具（tools）、智能体（agent）、干活循环（agent-loop）、权限范围（scope），另有第 7 个包 llm 负责模型请求侧的事。值得一提的是，scope 是六包里唯一不以服务形态存在的包。整套架构没有特权内核——也就是说没有任何一块是「谁也动不得」的，一切都可以由补丁替换。

图 1：dsh 的四层架构——从 5 个入口进来，经 4 层配置组装，落进插件容器，底下是三个来源的插件池
3.2 一轮干活的循环
把这层想成经理接单：一轮工作（turn）就是从你把任务丢进来，到把攒下的输入全部办完；每一轮里要做几件任务，每件任务（step）就是问一次模型、再把它要的工具活儿整批干完；某件任务失败了还要重试（attempt），重试不行才记下失败。像公司里「接单—派活—验收—记账」的小循环。

实际运转是三层套着转的：最外面由启动动作（kick）驱动一个「只要还有活就继续」的大循环；中间的轮次（turn）管边界，一轮开始、结束都有明确的事件通知；里面的步骤（step）管一次请求加它发起的工具调用。每走一步的固定动作是：先认领输入、看清楚这次模型能用哪些工具、组装提示词、过一道「开工前决策」、让模型流式回答、把回答记下来、整批执行工具、然后这一步收尾。轮次里如果这一步没有发起任何工具调用、后面也没有排队的新输入，这一轮就到此结束。

还有几条规矩：下一步的历史从台账现算，不靠记忆往下传；塞进新任务会唤醒新一轮（followup），干到一半插话不新开轮次（steer），只插入不唤醒是 inject；轮次开头的空批次不消耗模型调用；工具默认最多 10 个并行，改成 1 就是串行，随时可改。

图 2：一轮干活的循环——收输入 → 组提示词 → 模型回答 → 执行工具 → 记台账，没工具就收尾
3.3 工具出门的关卡
员工要动公司资产，得过一串关卡：先查工牌（参数在一切策略之前就冻结，想改也改不了）→ 该签字的先找人审批 → 门卫做终审（守卫，只负责拦、不负责放）→ 正式执行 → 事后检查 → 最后落盘记台账。审批这条规则是「找不到签字人，默认不放行」——跟现实里很多流程「找不到人就先放行」正好相反，宁可卡住也不放水。

顺序上，参数先冻结，然后进入查工牌环节（pre-execute，执行前决策）：这里只有四种结果——放行、拦下、取消、或者去问人（ask）。选了 ask 就走人工审批；还有一道单调守卫的关卡，态度永远是「只拒不放」，不会替你放行。真正在执行时，工具被一层「环绕」包住，超时、失败重试都在这一层处理；执行完还有事后检查（post-execute），结果可以被接受，也可以被拦下；收尾时统一整理内容、发出工具结果事件，中途抛出的错误也统一归一成「出错了」的样子交差。另外，工具自己的元数据（比如超时设置）只给关卡内部看，不给模型看。

图 3：工具出门的关卡——查工牌 → 审批（ask 分支）→ 门卫守卫 → 执行 → 事后检查 → 落盘
还有一条容易被忽略的细节：被过滤掉的工具，对模型来说和根本不存在的工具长得一模一样——模型不会知道「有这东西但被藏起来了」。
3.4 台账与签字
先说台账：公司的规矩是所有事实先记进台账，报表随时从台账重算——而且这本台账跟现实账本不一样，现实账本还能涂改，这本只能往后追加，改不了也删不掉。再说签字：审批走「找不到签字人就默认不放行」的路线，宁可停下来等人，也不自作主张放行。（当然，现实里很多流程找不到人反而先放行，这里正相反。）

台账这头，会话日志是唯一事实源，只追加、不修改。往里记一笔（append）只是尽力而为，真正保证「电脑崩了也不丢」的是刷盘（flush）动作：日志默认带压缩和校验、一批一批地落盘。日志的头信息和正文分开存。真崩了怎么办？持久层一个字都不改，由读的一方在恢复时补一条合成的「被中断」结束记录——这种结束标记从不由干活循环现场发出，只在恢复时补记写入。日志格式版本三处（写入、定稿、发布）保持一致，当前都是 4，对应发布标签 dsh-v0.2.0-rc.2。

签字这头，审批结果一共四选一：允许这一次、拒绝、取消、找不到应答者。系统只认「允许这一次」这一种放行答案；策略只有 ask（每次都问）和 never（从不问）两档，never 在分发之前就被强制生效。万一找不到该应答的人，结果就是「找不到应答者」——失败即关闭，默认不放行。所有审批动作都会留下成对的审计记录（问过、怎么定的），审计只进台账，不塞给模型看。还有一条安全底线：恢复会话后，那些处于「已武装」状态的目标不会自动替你干活，得有人重新授权才动。

一句话收尾：dsh 把「发生了什么」交给台账、把「能不能做」交给签字，两头都选了保守路线——台账宁可补记不改写，签字宁可卡住不放行。
4 举例说明
把 dsh 想成一家公司里的 AI 员工：你交代一句活，它自己领活、干活；要动公司的文件，得先查工牌、找人签字、过门卫；干完整本记进台账，下次接着上回的记录往下干。先有这个画面，再对照它的真实流程。

dsh 真实的流程就是四段：用户发消息（或定时触发）→ 会话循环 → 工具加审批 → 结果落日志。它并没有一个「按规则分派任务的中台」——消息统一进同一个收件箱，排进下一轮还是下一步、要不要唤醒，由调用方选定（followup / steer / inject 是同一个 send 的三种固定预设别名）。下面看两个具体场景。

4.1 场景一：同事提了个需求，AI 全程处理

同事提了个需求，AI 全程处理

1
需求进收件箱。同事发来一条消息（或者定时任务到点触发），新消息先进收件箱。消息有三种接法：followup 排进下一轮并唤醒会话，空闲时直接开轮；steer 排进下一步的边界（运行中等下一个步骤边界被认领，空闲时也开轮）；inject 只排队、不唤醒，等下次开轮才被认领——三种是同一个 send 的固定预设别名。
2
开一轮干活、认领输入。轮次的定义是「把已接纳的输入排空」。开轮后先认领这批输入，认领这个动作也会记进台账。
3
组装提示词、模型开答。先解析这一步模型能看到哪些工具，再组装提示词，过一道 pre-step 决策——如果被拒绝、或者认领后是空批次，这一轮不消耗模型调用；否则模型开始流式回答，回答记成一条助手消息。
4
要动公司资产，先过三道关。模型要动文件就得调工具。参数在一切策略之前先冻结、不许改；然后查工牌（pre-execute：放行 / 拒绝 / 取消 / 要签字四个分支）→ 要签字（ask，弹出审批卡片）→ 门卫终审（单调守卫只会说「不」，永远不会替谁放行）。
5
签字只认「允许一次」。审批有四种结果：只有 allowed-once 才放行，而且只授权这一次；找不到签字人就默认不放行；配置成 never 的话，在分发之前就强制拒绝，应答的人也绕不过。签字过程的审计记录只进日志、不进模型。
6
干完整批记台账。工具真正执行（外面套着超时与重试的保护），执行完还有道事后检查，可以接受、阻止或替换结果，最后落一条工具结果进日志。整批工具默认最多同时跑 10 个，必须排队的独占类工具得等前面完事；工具出错会被归一化成标准的失败结果报给模型。
7
收轮、下次接着聊。这一步记结束；自然停止且没有待办了，再记轮次收尾、状态回到空闲。下次再发消息，历史从台账重新派生，接着原对话往下走——不会失忆，也不会把你上回的话重复塞一遍。
图4：一条需求从进收件箱到收轮的六步（含工具三道关与台账）
4.2 场景二：一次签字

再看一个小场景：模型要删一个文件——查工牌时策略是 ask，于是弹出审批卡片；你点了「允许一次」，门卫终审放行，工具执行一次，结果记进台账。同一张「允许一次」不能重复用，下一次同样的请求还得再问一遍。如果你一直没应答，结果就是「无人应答」，默认不放行；如果策略配成「从不」，则在分发之前就直接拒绝，谁都绕不过。

并行提效

活儿并行干，默认 10 个一起跑

工具整批执行时，默认最多同时跑 10 个（配置成 1 就变成一个一个来）；互相依赖、必须排队的独占类工具会排在后面，不会互相撞车。一批活儿一起干，总比排着队一个个来快。

协作式取消

临时喊停，不白干

取消是协作式的：已经收到的内容会用 interrupted 标记保住，没来得及派发的工具调用会补一条中止前的合成结果；失败重试不会重新组装提示词，也不会把你的消息再塞一遍。

崩溃可恢复

账本扛得住崩溃

日志仅追加：平时的写入尽力而为，flush 之后才保证崩溃也存活；JSONL 默认 Zstd 压缩加校验和，逐批落盘（fsync）。崩溃后持久层一个字不改，恢复时由读的一方补上 interrupted 结束事件，会话接着走。

双平面可观测

回放、实时两本账各管各的

持久回放的事实记在会话事件里，供审计与重建；实时协调走 agent 域，只服务当前运行。审批的 asked/decided 审计也只进日志、不进模型——模型看不到签字过程，只看到放行结果。

还有一条容易被忽略的定性事实：工具的内部配置（比如超时、并发安全这类参数）不投影给模型，模型只看到名字、说明和参数。代价是被过滤的工具和压根不存在的工具，对模型来说无法区分——它不知道自己是「被禁止用」还是「根本没这功能」。这是能力暴露上的一处取舍，原文对它的取舍权衡 [原文未提供此方面信息]。

一句话总结：dsh 的「效果」不是跑分数字，而是四件可对照机制核实的事——默认并行 10 个提速、协作式取消保住已收到的内容、flush 级持久化让崩溃可恢复、回放与实时分两本账让审计有据可查；跑分类量化对比 [原文未提供此方面信息]。
6 解决了哪些痛点？
一家公司最常见的几种毛病：改制度得动章程原件、断电就丢账、找人代签放行、各部门各记各的账对不上、派人干活说不清谁干到哪一步、换账本怕把旧账迁丢。dsh 的设计，恰好冲着这些毛病去。

下面这张表把「没有它时」和「有了它后」摆在一起对照：

痛点 没有它时 有了它后
想改行为就得动内核 核心逻辑写死，改一处就得动内核，改动难保住、也难替换。 无特权内核：行为差异用 patch（配置补丁）替换，不必改内核；插件按依赖自动排加载顺序。
崩溃后会话接不上 断电后进度说不清，只能从头再来。 台账仅追加，flush 保证崩溃存活；恢复时持久层一字不改，由读的一方补上 interrupted 结束事件，会话接着走。
审批被绕过 口头把关：找不到人就默认放行，签过的字还能被反复使用。 fail-closed：审批四选一，只认「允许一次」且仅这一次；找不到签字人默认不放行；配成「从不」时在分发前强制拒绝，应答者绕不过。
工具的内部配置泄漏给模型 超时、并发这类内部参数一股脑给模型，既占地方又可能被带偏。 工具只把名字、说明、参数三样投影给模型，超时、并发安全等内部配置一律不给。
多 agent 派工混乱 各派各的，账目对不上，谁干到哪一步说不清。 统一接缝：subagent 像派外包小组（本地小组可续聊，外部小组交完报告就散）；workflow 是模型写的派工单，按单叫人；agent-team 是一个项目组，Lead 的日志就是组的档案。
迁移怕丢数据、版本各说各话 升级后旧账读不懂，版本号几处对不上。 格式版本三处对账、按相邻版本迁移，当前均为 4（发布 tag dsh-v0.2.0-rc.2）；header 与日志分开存。
一句话总结：dsh 把「改不动、断不起、拦不住、漏出去、派不顺、迁不动」六类毛病，分别用纯补丁内核、崩溃可恢复的只追加台账、fail-closed 审批、元数据不投影给模型、统一派工接缝、版本三处对账来解。
7 目前还有哪些问题？

任何项目在快速成长期都难免有"边跑边修"的部分。打个比方：这就像一家刚挂牌开业的公司——招牌已经挂出去了，客人也陆续进门，但内部流程还在不断调整，今天定的规章明天可能就改版了。下面先把"还没解决的麻烦"摆出来，再看团队正在怎么补。

还处在"公司刚开业"的阶段：README 里就直接预告，未来会有破坏兼容性的变更——也就是说，今天写好的对接方式，将来可能需要跟着改。

现存问题与挑战

  • 预览期随时可能"变规矩"。项目还处于开发者预览阶段，README 明确预告未来会有破坏兼容性的变更；公共 API 也处在 pre-stable（尚未稳定）状态，接口签名可能会调整。
  • 没有"一天最多开几轮会"的硬性规定。系统没有内置的轮次预算，要靠 agent/turn-stopping 这类扩展点自己限流——就像公司没规定一天最多开几轮会，得自己定规矩，不然可能开个不停。
  • agent-team 还是个实验中的项目组。它是 experimental（实验）包：没有消息重发和去重机制，历史邮箱里的消息只为回放保留；writeScopes（写权限范围）只是提示、不是真正的锁；任务的文件触及提示也只发重叠警告、绝不阻止操作。像一个刚成立、还在磨合的小组。
  • 权限范围不"遗传"。scope（作用域）是两层扁平结构，带作用域的注册不会继承给 subagent（子代理）——好比总部门签的权限，到了分部不一定自动生效，得重新报批。
  • 被"藏起来"的工具和"没有"的工具分不清。被 restriction（限制）过滤掉的工具，和压根不存在的工具，对模型来说无法区分——它不知道自己是"被禁止用"还是"根本没这功能"。
  • 恢复后要人先点头才自动干活。目标的 armed/disarmed（武装/解除）状态有意不参与回放，恢复或 fork 之后，需要一次人类授权才开始自动工作。这是有意的安全设计，但也意味着多一步人工确认。

正在改进的方向

  • 格式版本"三源纪律"。版本号同时写在常量、定稿基线、发布记录三处；发布前不得推进发布记录，主干永不降版——像账本三处对账，防止版本号各说各话。
  • 事件目录由脚本生成、再跑校验。持久化事件清单不再手写，由脚本从源码生成，检查脚本会验它有没有过期；工具目录另有 glob 完整性守卫，漏登记会直接报错。
  • 能力 seam（接缝）服务拓扑表由脚本生成。不再靠手写维护，脚本一跑就得到最新表，减少"文档和实际对不上"。
  • 经验教训有 postmortem（复盘）文档沉淀。目前有 4 篇复盘文档，踩过的坑写下来，不再重复踩。
  • 双语成对维护、发布有纪律。文档（连测试目录的说明）中英成对，还有测试校验双语一致（如 doc-standard 测试）；配合版本三源纪律形成发布前的检查链。
一句话总结：问题主要集中在"预览期接口未定型、实验组件尚不完善、限流要靠自己"；改进方向则集中在"用生成和校验代替人肉维护、用复盘沉淀经验"。
8 主要应用场景

同一个内核，换不同的"门面"，就能覆盖从个人日常使用到大规模自动化分工的多种场景。就像同一家公司，既可以开街边门店直接接待散客（web），也可以承接批量代工订单跑一次就收工（headless），还能把自己的生产线租给别人建厂（sdk）。

🌐

浏览器里日常使用

web 方式：常驻本地服务器（127.0.0.1:3080）加浏览器界面，打开网页就能用。

⚡

脚本/CI 自动跑一次任务

headless 方式：一次任务跑完就退出，输出 --json 事件流，适合自动化流水线。

🧩

给自己的程序当内核

sdk / sdk-minimal 方式：常驻 stdio JSON-RPC，把能力嵌进你自己的程序；另有 Python wheel SDK。

🔌

接进编辑器/自动化工具

acp 方式：常驻自动化 stdio，方便编辑器、自动化工具等外部程序对接。

🖥️

桌面应用形态

desktop 方式：Electron 应用，监听系统分配的端口，装在电脑上直接用。

🤝

多 agent 分工协作

subagent 支持本地/外部两种；workflow 模型像"写派工单"一样分派任务，让多个代理各司其职。

按运行方式分类

上面六张卡片里，前五张各对应一种"运行方式"（profile），第六张的多 agent 分工是横切能力、不属于某个窗口。把前五张排成下表——就像同一家公司的营业窗口，外观不同，内里是同一套后厨（sdk 与 sdk-minimal 合并成一行）：

运行方式 一句话场景 特点
web 在浏览器里日常使用 常驻本地 server（127.0.0.1:3080）+ 浏览器界面
headless 脚本/CI 自动跑一次任务 跑完即退出，--json 事件流输出
sdk / sdk-minimal 给自己的程序当内核 常驻 stdio JSON-RPC；另有 Python wheel SDK
acp 接进编辑器/自动化工具 常驻自动化 stdio
desktop 桌面应用形态 Electron，监听系统分配端口
HMR（热更新）不是全局开关，由每个运行方式自己决定：基础层默认开着，headless、sdk、acp 关掉，sdk-minimal 根本不带——就像各窗口自选装不装自动叫号屏：装了的改菜单立刻生效，没装的得关窗重开。
怎么选？自己在浏览器里用选 web；要自动化跑批选 headless；要把能力嵌进自己的程序选 sdk；要对接编辑器等外部工具选 acp；想装个桌面应用选 desktop。
