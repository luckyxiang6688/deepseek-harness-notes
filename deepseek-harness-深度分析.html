DeepSeek Harness（dsh）深度分析

一切皆插件的开源 agent 运行时：从事件驱动的插件内核，到 turn/step 三层循环、工具执行管线与 fail-closed 的持久化和审批体系

1 总览与脉络
DeepSeek Harness（下称 dsh）是什么、从哪里来、为什么值得读。本节给出一句话定义、项目背景与演进脉络，以及三条核心价值主张；后续章节再逐层拆开它的原理与运行流程。
一句话理解 dsh

dsh 是一个「无特权内核」的智能体运行框架：核心不内置任何不可替换的大脑或手脚，只定义服务接缝（能力接口的三角色契约）与事件扩展点；模型调用、工具执行、会话持久化全部由可插拔、可替换的插件提供，按 profile（随发行交付的具名组装）组装成 Web、Headless、SDK 等不同形态，并把一切事实写进 JSONL 事件日志。类比来说：如果大模型是发动机，agent harness 就是整车的底盘与总线——它不生产智能，而是把模型、工具、会话与配置组织成一个可运行、可替换零件的产品。

1.1 背景与演进

dsh 由 DeepSeek AI 开发，是开源的 agent harness（智能体框架），构建于「一切皆插件」的架构之上，由 Cordis 驱动，其设计参见论文 A Programming Paradigm for Spatiotemporal Composability（arXiv:2608.25512）。项目当前处于开发者预览（Developer Preview）阶段，正在快速迭代，官方明确提示「未来将出现破坏兼容性的变更」，运行前须阅读 SAFETY.zh.md 安全说明。许可证为 MIT，bibtex 引用条目年份为 2026。

发行形态上，dsh 随发行提供 5 个 profile：web、headless、sdk、sdk-minimal、acp，每个 profile 是一份具名组装，列出自己叠放的组合包，决定这次启动装载哪些能力。双入口的启动方式：

npx 一行启动

npx @deepseek-ai/dsh web 默认在 http://127.0.0.1:3080 启动 Web UI，本机启动还会打开默认浏览器；传入 --no-open 仅运行服务器不打开页面。

源码运行

git clone → pnpm install → pnpm run build → pnpm dsh web；开发时 pnpm run dev:web 在单终端内完成构建、启动，并在源码修改时重建 client bundle。

1.3 核心价值
无特权内核

核心没有不可替换的「特权代码」，一切皆可由 patch（配置补丁）替换；连 HMR（热模块替换）也是按 profile 装载的插件——base 启用 dsh-hmr，Headless/SDK/ACP 禁用，sdk-minimal 干脆不含。

事件即扩展点

新行为不改内核循环，而是监听事件：会话事件、agent/* 与能力事件（fs/*、tools/*、telemetry/*）构成三域，waterfall、bail 等五种分发模式覆盖改写与拦截场景。

注册是可逆副作用

一切贡献都经 ctx.effect() / ctx.on() 注册，注册被撤销即插件卸载；加载顺序由服务依赖表达而非手动编排，因此拆卸天然安全。

2 核心原理
dsh 的四条地基：一切皆插件的装配模型、capability seam（能力接缝）的三角色契约、事件的五种分发模式，以及轮次与步骤的运行语义。理解这四条，后面读配置层与 agent-loop 源码都会顺很多。
2.1 一切皆插件与无特权内核

dsh 构建于「一切皆插件」架构：插件是实现 Service（服务）的对象，上下文（context）是服务容器，服务占稳定的 ctx.<key> 槽位（如 ctx.tools、ctx.llm、ctx.sessions），依赖通过 inject 声明，加载顺序由依赖关系表达而非手动编排。核心包共 7 个（core/session、system-prompt、tools、agent、agent-loop、scope、llm/llm），它们同样以插件身份装载——没有特权内核，一切可由 patch 替换。

配置合成按固定优先级分层，共 4 层：profile 组合包 → cordis.patch.yml → home patch → --patch overlay（细节见第 5 节）。可用 dsh --profile web --dump-config 打印最终配置树，验证哪一层覆盖了哪一项。因为注册皆为副作用，插件被卸载时其注册自动被撤销——这是「可替换」在运行时的另一半含义。

2.2 capability seam：三角色契约

capability seam（能力接缝）是 dsh 拆分可替换能力的标准单位，由三个角色构成，缺一不可：Service Definition（服务定义，声明接口与语义）、Provider（提供者，给出实现）、Consumer（消费者，按接口调用）。以 packages/shell 为例：dsh-shell 是 Definition，dsh-bash-local / dsh-bash-sandbox 是其中可互换的 Provider，dsh-tool-bash 是 Consumer——换 Provider 不动 Consumer，正是接缝的意义。

图2：capability seam 三角色关系（以 packages/shell 为例）
2.3 事件五种分发模式

事件就是 dsh 的扩展点，一次注册通过 @mode 标签声明分发模式，共 5 种：

模式语义
emit广播通知，逐个通知监听者，用于「发生了某事」。
waterfall链式改写：监听者签名是 (...args, next)，依次改造共享参数，必须调用 next() 才把控制权交给下一位。
parallel并行执行全部监听者，互不等待彼此的完成顺序。
serial串行执行监听者，按注册顺序逐个完成。
bail短路返回：停在首个 bail 值，后续监听者不再执行。

两条硬规则：waterfall 监听器必须调用 next()——不调用即短路整条链；而对单决策事件（如拒绝/通过）而言，短路本身是设计意图。配套纪律是：每个注册都应有对应的 disposer（资源释放函数）；拦截类需求优先走事件，直接能力调用优先走服务方法。

2.4 轮次与步骤语义

dsh 把一次会话运行切成两层：轮次（turn）是一次「排空已接纳输入」的过程，包含零或多个步骤；步骤（step）等于一次模型请求 + 其工具。因此「模型答完但没调工具」是恰好一个步骤的轮次，「拒绝或空批次」则可以是零步骤的轮次。轮次之外，交互段由真人输入轮次界定。这三个词在后文的事件名（turn/start、step/end）里会反复出现。

3 完整流程
从 followup 进入 inbox 到 turn/end 收束，一个轮次端到端经过哪些事件、每一步数据如何变化、失败走哪条路。本节是理解 agent-loop 源码的地图。
3.1 双平面原则
持久回放看 session/event，实时协调看 agent/*

dsh 把事件分成两个平面：持久回放事实记在 session/event（会话事件），供回放、审计与 SDK 重建 transcript；实时控制与状态走 agent/* 域，只服务当前运行的协调。规则很硬：SDK 要回放 transcript 应消费 session/event，agent/* 仅作实时协调——把实时事件当历史真源读会得到不完整的账本。

4 模块详解
本节按包拆开 dsh 的主干：六个核心包如何分工、Agent 句柄如何对外暴露、事件目录如何组织。所有行号与事件名均取自仓库文档原文。

4.1 核心六包主干

core 子系统由六个主干包构成：session、system-prompt、tools、agent、agent-loop、scope（docs/subsystems/core.zh.md 行 9-20）。加载顺序由服务依赖表达；其中 scope 是唯一非服务包——零依赖库，位于 session/ 与 system-prompt/ 之下被它们消费而不形成环（行 20）。

  • session — 会话持久层。Session 仅追加日志，承载十三种核心事件（行 426）；deriveMessages() 从日志派生模型可见历史；TurnBoundaryProjection 提供轮次边界的四字段投影（行 501-510）。JSONL v0 文件名为 session.jsonl[.zstd]，v1+ 为 session.vN.jsonl[.zstd]（architecture.zh.md 行 130）。
  • system-prompt — 系统提示词组装：提示词片段与工具 schema 的组装（architecture.zh.md 行 60；core.zh.md 行 14）。
  • tools — 工具注册与执行策略层。schemas() 只向模型投影 name/description/parameters，timeoutMs、isConcurrencySafe、presentCall 不泄漏给模型（subsystems/tools.zh.md 行 11、66）；条件准入 when 经 ctx.tools.resolve() 每步解析（行 182）。
  • agent — Agent 抽象与句柄层。定义 Agent 接口（cancel/whenIdle/runMaintenance/send）与 AgentHandle={agent,dispose()}（行 45-48、65-120）。
  • agent-loop — 循环实现层。实现 AgentFactory 并注册到 ctx.agents（agent-loop/README.md 行 89）；index.ts 中 AgentLoop implements AgentFactory（:291），inject 六项（:292），maxParallelToolCalls schema default=10（constants.ts:6，:296）。
  • scope — 唯一非服务包，不以 Service 形态参与容器。

架构文档把 llm/llm 与上述六包并列为 7 个核心包（architecture.zh.md 行 57-65），本文依 core.zh.md 的「主干六包」口径单列，llm 作为第 7 包合并说明：它负责模型请求侧能力，被 agent-loop 的 prepareRequest/buildRequest/流式路径消费；架构表给它的职责是「消息与流式词汇表，以及适配器 seam」（行 65）。

图4：核心六包与 llm 第 7 包的 ctx 键关系（环形）

4.2 Agent 句柄与接口

对外暴露的最小单元是 AgentHandle = { agent, dispose() }（core.zh.md 行 45-48）。Agent 接口的核心方法是 cancel、whenIdle、runMaintenance、send；其中 followup、steer、inject 是 send 的别名（行 59、65-146）。在 agent.ts 中这三者与 cancel 一起按路由分发（agent.ts :179-191）。

可替换性的关键约束：扩展插件只依赖 agent 包、绝不依赖 agent-loop，因此循环实现可以整体替换（core.zh.md 行 20）。循环对外经 ctx.agentLoop 提供 create / createAgent / resume（行 548-584；index.ts :668/:717/:754），并以 AgentFactory 身份注册到 ctx.agents（agent-loop/README.md 行 89）。

恢复语义由 index.ts 固定顺序保证：persistence.open 拿 write 独占 → 冷读 → interruptedTurnClosers → sessions.prepare（:789-804）；拆除按逆序五步执行并以 AggregateError 汇总（:498-545），另有三个 owner 融合的 AbortController（:473-486）。

4.3 事件目录

架构文档把事件划分为三域（architecture.zh.md 行 73-75）：

  • 会话事件 — 以 session/event 为轴，Session 仅追加日志并承载十三种核心事件（core.zh.md 行 426）；session/event 的监听者最多，32 个包（event-producer-consumer.zh.md 行 77）。
  • agent/* — 实时协调域，用于轮次/步骤级协作（如 agent/pre-step、agent/turn-stopping、agent/request-error、agent/inbox/inserted；其中 agent/inbox/spliced 是入日志的会话事件，不属实时域）。
  • 能力事件 — fs/*、tools/*、telemetry/* 三个前缀（行 73-75）。

事件是多对多关系，所以官方用表格而非大型关系图来描述（event-producer-consumer.zh.md 行 8）；应用级监听者不在包矩阵内（行 10）。生成矩阵覆盖 emit/serial/waterfall/parallel 四种模式的产出（行 13）——注意此处列四模式，而 cordis 入门文档列五模式（emit/waterfall/parallel/serial/bail，cordis-primer.zh.md 行 21-27），二者口径不同，前者是「生成」矩阵。

事件即扩展点：文档明确「选对事件域是大多数改动的第一个决定」（architecture.zh.md 行 71）。典型高频事件：agent/pre-step waterfall 有 18 个包监听（行 24）；tools/pre-execute、tools/execute、tools/post-execute 均为 waterfall，由 tools 包派发（行 88-90）；tools/result emit 的监听者含 subagent、tool-present、ui-trajectory（行 92）。

5 架构设计
dsh 的「无特权内核、一切可 patch」哲学落在两处：四层 patch 组装出运行配置，事件三域承载全部扩展行为。

5.1 四层 patch 组装

dsh 没有特权内核，一切可 patch（architecture.zh.md 行 11）。配置按四层优先级从低到高叠加（行 25）：

  1. profile 组合包 — 所选 profile 自带的默认组合；
  2. cordis.patch.yml — 项目级 patch 文件；
  3. home patch — 用户主目录级 patch；
  4. --patch overlay — 命令行传入的覆盖层，优先级最高。

可用 dsh --profile web --dump-config 查看组装后的最终配置（行 34）。

HMR 分布（行 27）：base 启用 dsh-hmr；Headless、SDK、ACP 三个 profile 禁用它；sdk-minimal 则根本不包含 dsh-hmr。

5.3 事件即扩展点

三域事件（会话 / agent/* / 能力 fs|tools|telemetry）构成全部扩展面。文档给出两条硬规则：

  • 选对事件域是大多数改动的第一个决定（architecture.zh.md 行 71）——动手前先确定你挂在哪一域。
  • waterfall 必须调用 next()（行 110）。按 cordis 入门文档，waterfall 监听器签名是 (...args, next)，不调用 next() 即短路（cordis-primer.zh.md 行 35）；单决策事件短路是设计意图（行 39）。

五概念与五模式是使用事件的前提：插件是实现 Service 的对象、上下文是服务容器、inject 声明依赖、类型化事件通信、注册是可逆副作用（行 9-13）；模式为 emit/waterfall/parallel/serial/bail（行 21-27）。配套纪律：每注册配 disposer（行 51）；拦截优先走事件、能力调用优先走服务方法（行 49）；加载顺序由服务依赖表达（行 11）。

新行为的归属由「新行为归属映射表」给出（architecture.zh.md 行 150-171，20 条映射）；seam 承担三角色（行 140）。

6 关键机制详解
本节深入两个最常被改动的机制：agent-loop 的三层嵌套循环，以及工具执行的三瀑布一守卫管线。

6.1 agent-loop 三层嵌套循环

三层循环：kick / turn / step 的边界与事件

▼

外层 kick：while (await turn())（agent.ts :268-281）——只要 turn 返回真就继续下一轮。取消是协作式的，以 interrupted:true 为锚（README :75、:120）；未派发即取消归为 ABORTED_BEFORE_DISPATCH（:184）。

中层 turn：一轮 = 零或多个步骤（architecture.zh.md 行 85）。事件序列固定：turn/start(:336) → preStep(:347) → step/start(:361) → step(:370) → step/end(:388) → agent/turn-stopping(:396) → turn/end(:422)。Phase 三态见 :53-61；StepEndReason 为 completed|max-tokens（:63）；max-tokens 粘滞（:373）。首步为空直接 completed（:356-358）。agent/turn-stopping 是 serial 模式，可 steer 续轮（core.zh.md 行 1125-1147）；工具结果带 concludesTurn 则该步终止轮次（行 1127）。无内置轮次预算，靠 agent/turn-stopping 决定（README :220）。

内层 step：一次模型请求 + 其工具（architecture.zh.md 行 85）。step 内部：prepareRequest(:445) → 准入(:460-471) → buildRequest(:479) → 流式(:480) → agent/request-error 可 retry(:548-563) → assistant/message(:576) → 无 tool-call 则 completed(:587)。用户消息仅 first attempt 准入(:463-478)。maxParallelToolCalls 在 :588-593 读取，默认 10，1=串行，实时修改对下一批生效（README :55）。preStep = claim(:287) → tools.resolve(:292) → assemble(:294) → agent/pre-step waterfall(:296-306)；agent/request waterfall(:630) 只可改采样等其他控制参数，改 provider/model/effort 即抛错拒绝该步(:635-640)；request/header 理由四值(:677-690)；deepFreeze(:727-734)；ToolCallRecovery 补记(:363-385)。

失败路径：请求错误经 agent/request-error 决定是否 retry；取消经协作式 interrupted 锚；未派发取消 → ABORTED_BEFORE_DISPATCH。

空步旁路：首步若为空直接 completed(:356-358)，不进入工具阶段。

会话侧配合：不带 sessionId 时新建 ${id}-session-<uuid>（README :47）；inbox 变更提交 agent/inbox/spliced（:71）；prompt 的 in-history 非空变更采用追加方式，以保留缓存前缀（:164）；事实先落日志再派生下一步（:75）。创建入口 create(:668)/createAgent(:717)/resume(:754)，sessionId 互斥（index.ts :278）。

6.2 工具执行管线

阶段顺序（tool-execution-pipeline.zh.md 行 8）：tools/pre-execute 瀑布 → 单调守卫 → tools/execute 与 tools/post-execute 瀑布。其中 projectContent 在后置策略之前，finalizeContent 与 tools/result 在其之后。三瀑布均由 tools 包派发（event-producer-consumer.zh.md 行 88-90）。

  • approval 拦截点：ctx.approval 一次性询问，缺省或不可答即 deny（行 18）。
  • 单调守卫：守卫 deny 或 abstain 即拒绝，identity protected（行 16）。ToolGuard 没有 allow 分支，监听顺序不可撤销拒绝（subsystems/tools.zh.md 行 458-469）。
  • 决策类型：PreToolDecision 四分支 allow/deny/cancel/ask（行 543-547）；PostToolDecision accept|block（行 555-558）。
  • 参数冻结：参数在策略前物化并冻结（tools.zh.md 行 456、561）——策略看到的即模型看到的。
  • 错误归一化：pipeline/result 快照抛出归一化为 isError（pipeline 行 25；tools.zh.md 行 527-529）；错误码 INVALID_ARGS/INVALID_TOOL_OUTPUT/UNKNOWN_TOOL（tools.zh.md 行 159、563）。
  • 观察者只读：tools/result 观察者不可变换结果，且失败被隔离（行 563）。

作用域限制：fs/write-intent、fs/edit-intent 仅作用于 tool-fs 变更（pipeline 行 21）；工具自有会话事件包括 todo/write、fs/observed、hook/invoked、hook/result、tool/ptc-dispatch（行 22）。additionalContexts 按 FIFO 注入（行 28、63）。PTC 模式下 run_code 及其子调用同入流水线（行 66）。ToolExecutionMode 为 parallel|exclusive，exclusive 形成顺序屏障（tools.zh.md 行 393-398）。

价值主张：流水线无需修改 agent loop 即可执行策略/钩子/沙箱/守卫/改写/观测（pipeline 行 8）。

6.3 两机制的共同设计

两条在循环与管线中同时出现的原则：

  • 事实先落日志，再派生下一步（agent-loop/README :75）：step 产生的事件先写入 Session 追加日志，后续历史由 deriveMessages() 派生（core.zh.md），因此恢复与重放走同一条路径。
  • 身份冻结 + 观察者只读：工具参数在策略前物化冻结（tools.zh.md :456、561），请求侧 deepFreeze（agent.ts :727-734），tools/result 观察者不可变换（tools.zh.md :563）——写路径集中在少数 waterfall，观察者不构成旁路。

7 多 agent 与编排
dsh 的多 agent 能力分三层交付：subagent 是常规交付的执行层 seam，workflow 是可选的脚本编排引擎，agent-team 是 experimental 的团队领域。三层成熟度不同、真源不同，但通过同一组 ctx 抽象与事件通道咬合——workflow 的 agent() 正是经 subagent seam 启动子级并归属 parent。

7.1 subagent：执行层

所有后端统一走 startActivation 这一入口：能力标记先校验请求选项，prepareContinuable 选择本地 Agent 创建，start 选择一次外部执行（subagent.zh.md 行9）——本地与外部由此成为同一 API 下的双泳道，而不是两套接口。SubagentCapabilities 用四项布尔能力声明后端边界：agentOptions / agentPreset / outputSchema / depthLimit（行20-26）；provider 缺能力即在 start 拒绝、不做静默降级（行105-116；错误码 UNSUPPORTED_CAPABILITY 经源码核验）。

  • delivery 二元语义（行43、176）：'parent' 把结束通知投递给父级模型；'caller' 只把结果返回调用方并抑制结束通知——面向模型的工具用 parent 回传，workflow 与 code mode 消费者等 caller 结果，不向父代理注入多余消息。
  • preset 归属（行130）：仅 spawn 支持独立 agentPreset；省略选择与 fork 都继承父方的活跃组装。结构化结果提交会关闭该 activation 的输入，之后的冷恢复不再继承 outputSchema（行132）。
  • StopReason 五种（行275-286）：completed（正常结束）｜aborted（请求信号或处置取消）｜error（模型或传输失败）｜max-tokens（触 token 上限）｜refusal（子级拒绝任务）。
  • diagnostic 安全上限（行260）：后端诊断至多 4096 UTF-8 字节，且不得含工具输入、文件内容或凭证；消费方将其与 output 分开呈现。
  • 消息与中断（行176、222-225）：sendMessage 按确切在线发送者实例授权，仅允许相邻本地代理通信；interrupt 两种授权形态 user（携 parentSessionId）与 ancestor（携 agent）。
  • 可发现性与遍历（行9、381-391）：descriptor 不可用的历史子会话以 mode: 'unknown' 保持可发现，但不授予继续执行能力。listDescendants 以稳定前序递归读取目录，每行携带父级与深度，direct child 的 depth = 1；外部条目是无本地 Session 的叶节点。
  • 失败不互踩（行233）：清理失败单独报告，不覆盖已捕获的执行结果——结果与父级通知保留它，dispose 拒绝，而在线 subagent/end 事件报告 error。
  • 生命周期事件（行605-679）：subagent/start、subagent/end、subagent/provider-added、subagent/provider-removed 均为 emit；start/end 复用同一 delegating parent carrier，生命周期成对到达同一批 scoped 受众。

7.2 workflow：脚本层

workflow seam 是一个由模型编写、用来启动 subagent 的编排脚本引擎，属于可选能力，且每上下文只有一个引擎槽 ctx.workflowEngine——与 bash 同模式，一个上下文一个引擎实现（workflow.zh.md 行5）。启动请求 WorkflowStartRequest 必填 parent: Agent（行13、33）；meta/args 是纯 JSON，经 schema 校验且绝不求值脚本文本（行13）——脚本是数据，不是被 eval 的代码通道。

  • 结果与生命周期（行65、75-90、95、98-111）：WorkflowResult.stopReason 三态 completed | cancelled | error，另有 agentsStarted 计数；result 绝不 reject；dispose 幂等且在每条路径上必调。
  • 错误分类（行116）：WorkflowError.fatal 用于脚本钩子误用（错误参数、未知或延迟的 agent() 选项等）；parallel() / pipeline() 的失败直接重抛。
  • 6 个 emit 事件（行120）：workflow/start、workflow/phase、workflow/log、workflow/agent-start、workflow/agent-end、workflow/end。每个监听器异常隔离，只记日志，payload 发递前克隆——观察者崩了不碰运行。
  • 持久记录（行124、126）：顶层 dsh-tool-workflow 消费方把展示事实投影到父 Session，持久记录 tool-workflow/run-start | run-end；首次 append 失败即禁用本运行的后续写入。日志尾部缺成员 end / run end 是有效中断证据而非损坏。
  • 配对与展示（行164、186、41、246）：agent-start/agent-end 按 agent.seq 配对，终止路径合成 cancelled end；phases 仅供进度展示，无执行语义。

与 subagent 的接缝在归属上：workflow 的 agent() 经 subagent seam 启动，子级归属 parent——脚本层不发明自己的子代理语义，全部下沉到执行层统一的 startActivation 泳道。

7.3 agent-team：实验层

agent-team 位于 packages/experimental/agent-team/src/types.ts（agent-team.zh.md 行5），是实验性隐式 Root Team 领域。TeamId 是使用独立品牌类型的 root SessionId，TeamTaskId 形如 task-<n>（行9）。Lead Session 的日志即 Team 真源——没有第二份权威状态。

  • 成员与 roster（行13-24）：成员 context: 'fresh' | 'fork'；每个成员从 provisioning 开始，只到达终态 roster phase active 或 failed；roster 视图中的 running/inactive 是另行派生的，不进成员生命周期。
  • 消息投递（行41、28-53）：每条消息尝试 Steer 投递——running 目标在最近的步骤边界收到，inactive 目标在加载时启动一个轮次，否则留待冷恢复。Team 不为新消息提供 outbox，也不做重发去重；历史 mailbox 类型仅为回放保留。
  • 任务 DAG（行58-71、74）：每条 task event 存完整快照，revision 是 compare-and-set 值、每次变更 +1；blockedBy 无环；TeamTaskStatus 为 pending | in_progress | completed | deleted。
  • writeScopes 不是锁（行58-71）：writeScopes 是提示性路径前缀，只作警告提示，不提供互斥。
  • 投影与回放（行80、110-120、125）：Web 投影经 SessionProjectionMap.agentTeam，failure 报告首个被拒的持久记录；回放按 TeamId 选取，普通 fork 绝不进入新 Root。waitForChange 的 timeoutMs 介于十秒至一小时（行206-208）。
  • 权限分工：spawnTeammate/interrupt 仅 Lead 可调，createTask/updateTask/waitForChange 任意成员可调。

8 持久化与人工确认
dsh 把「事实先落日志」贯彻到两个方向：Session 日志是一切状态的真源（持久化子系统），approval 审计对是人工确认的真源（审批子系统）。两者的失败姿态一致——fail-closed：不修、不猜、不放行。

8.1 Session 日志即真源

持久化 seam 只暴露 create / open / stat / list 四个方法，没有平行的持久化事件类型；create/open 返回 SessionHandle（read / append / flush / close），每一次日志读写都经句柄流动，绝不经按 id 寻址的服务方法（persistence.zh.md 行7、11）。随产品交付的 provider 是 dsh-session-persistence-jsonl（行7、341）。

  • 单写者（行11、74-75）：第二次 open(id, 'write') 抛 SessionAlreadyOwnedError；读句柄上修改抛 SessionReadOnlyError；写所有权丢失抛 SessionOwnershipLostError。
  • append 是 best-effort（行68-91）：只有 resolved 的 flush 承诺崩溃后存活，flush 是唯一的 durability barrier。
  • header 分离存储（行137-188）：SessionHeader 独立于事件日志，含 version / id / createdAt / cwd? / parentSession? / isSeeded / origin? / delegationDepth? / agentPreset?；header 不进 SessionEventMap、不到 deriveMessages。
  • 存储形态（行341）：逐会话仅追加的逻辑 JSONL，默认存为带 checksum 的连续 Zstandard frame（可配置为原始行），append 逐批 fsync。
  • 格式状态（行102、191-193、319、357、359）：formatStatus: 'current' | 'migration-required'；SessionFormatUnsupportedError（本构建无法可靠解读）与 SessionPersistenceCorruptionError 严格区分。读方只读当前格式，未知词汇 fail-closed；未实体化会话崩溃后等于从未存在。

格式版本三源对照（session-format-status.md）：唯一手工维护的写入者常量 SESSION_FORMAT_VERSION（session-format-status.md 行20；常量在 packages/core/session/src/types.ts 行90，值为 4）；latestFinalizedVersion: 4，基线 persistence-changes/finalized/v4.json（行31-35）；latestReleasedVersion: 4，evidenceTag: dsh-v0.2.0-rc.2（行44-47）。写入者常量与已发布记录相等即表示写入者格式已发布（行22）；alpha/beta/RC 发布即确立已发布格式义务（行24）。更新纪律：发布前不得推进 release 记录，发布后在同一次双语更新中推进，主干永不降低（行54）；doc-standard.spec.ts 检查记录结构与双语一致，但不查 GitHub（行56）。

8.2 崩溃恢复：不截断、不修复，修复归读方

一个在轮次中途崩溃的日志以打开的 turn/start 而无 turn/end 结束（persistence.zh.md 行108-110）。持久层的立场是：不截断、不修复，只丢弃撕裂的物理尾部；语义修复是读方（resume）的职责——resume 计算 interruptedTurnClosers，为缺失工具错误、未闭合的 step/end 补齐记录，并合成 turn/end {reason:{kind:'interrupted'}}。由此 interrupted 成为唯一不由循环发出的 TurnEndReason——它标记的是「存储层观察到的中断」，而非循环自己的终止决策。

这条分工与 agent-loop README 的记载互为印证：resume 把 interruptedTurnClosers 作为普通批次追加，「语义崩溃修复是 agent 层的职责，而非存储入口」。存储保真、语义归层——两层都不越权。

8.3 approval：fail-closed 的四元组决策

ApprovalOutcome 是闭合四元组且失败时拒绝：'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'（approval.zh.md 行21-28）；allowed-once 仅授权所询问的那一个操作（行5、21）。ApprovalPolicy = 'ask' | 'never'（行33-46）：ask 委托给组合的应答者链，无应答默认 unavailable；never 确定性返回 rejected，根本不分发应答者。生效值 = 会话日志中最后一条 approval/policy 事件，setApprovalPolicy 是唯一写入路径（行33）。

  • 请求配对（行11-18）：每个请求获得全新的 ApprovalRequestId，将 approval/asked 与 approval/decided 审计对配起来。
  • 不携带参数（行53-73）：ApprovalRequest 有意省略工具参数，用 callId 挂到已流式输出的工具调用上——审批问题不重复搬运 payload。
  • 作用域（行86、117-119）：request() 要求发起请求的会话处于一个尚未结束的轮次内，因为审计对必须被轮次包住。
  • 失败归一（行119-123）：abort → cancelled；缺失、抛异常、不合规 → unavailable（fail-closed，非词汇值一律归一为 unavailable）。
  • 审计不进 transcript（行88）：审计事件仅写日志，不进入模型 transcript；模型可见的行为由调用方决定。
  • never 先于分发（行86）：never 在服务内部 waterfall 分发之前强制，prepend 应答者无法绕过。
  • 默认关闭：调用方除非拿到 allowed-once 否则一律拒绝；第一个应答占据唯一决策槽位；任一审计 append 在提交前失败 → 整个 request reject。UI 通道提供人类应答者，ACP 桥接层提供一次性机器决策。
图8：approval 决策树——四元组 outcome 全部由日志审计对承载，never 在 waterfall 分发前强制，失败路径一律收敛到 unavailable/rejected。

fail-closed 不是 approval 的局部癖好，而是全仓的默认失败姿态。capability-seams 文档把这条写成服务接线原则：「没有回答方时以 unavailable 关闭失败」（capability-seams.zh.md 行740，ctx.approval 行）——seam 可以没有实现，但不能默默放行。各子系统的同构表现：

9 优劣势与展望
把前八节的证据收拢成一张双面清单：dsh 的优势几乎都来自同一组设计选择（插件化、事件化、seam 化、日志真源、fail-closed），而它的代价——预览期兼容性、实验层的弱保证、scope 的扁平边界——同样来自同一组选择。
优势
  • 无特权内核：一切皆插件，服务按 core / seam / 组合包 / service 四类划分（capability-seams.zh.md 行8、653），角色字段 service|core|seam|bundle，连 ctx.agentLoop 也只是 bundle（行730）；消费方依赖抽象 ctx 键而非具体实现，没有绕过插件体系的特权路径。
  • 事件即扩展点：事件可被门禁拦截——如 ctx.fs -.event gate.-> pkg_fs_observation_policy（行650）；subagent/workflow 各自 emit 完整生命周期事件，新行为挂在文档化的扩展点上而非改循环。
  • seam 可替换：ctx.llm → llm-deepseek / llm-pi-ai / llm-replay，ctx.fs → fs-local / fs-sandbox / fs-ssh，ctx.shell → bash-local / bash-sandbox / pwsh-local（行678、743、734-735）——同一抽象键下多实现并存。
  • 事实先落日志：Session 日志即真源（persistence），Lead Session 日志即 Team 真源（agent-team），审计对仅写日志不进 transcript（approval 行88）——状态不是内存里的偶然产物。
  • fail-closed：审批默认关闭、无回答方 unavailable、未知格式词汇拒绝解读、限制工具与不存在工具不可区分——失败方向永远是「关小」而非「放开」。
  • 双平面可观测：运行时事件（subagent/start|end 等 4 事件、workflow 6 事件）与持久记录（tool-workflow/run-start|run-end、approval/asked|decided）构成两条互证的观测通道，Web 投影（如 SessionProjectionMap.agentTeam）从日志单向派生。
劣势
  • 开发者预览，不保证兼容：README 行13 明言处于 developer preview、快速迭代，「未来将出现破坏兼容性的变更」（THERE WILL BE COMPATIBILITY-BREAKING CHANGES）。
  • 无内置轮次预算：agent-loop README 行220——工具调用或 steering 会让当前轮次继续，限制失控轮次的策略必须从既有生命周期扩展点（如 agent/turn-stopping）自行执行取消。
  • agent-team 实验期弱保证：不为新消息提供 outbox 或重发去重（agent-team 行28-53），writeScopes 只是提示性路径前缀、不是锁（行58-71）。
  • scope 不继承：两层扁平结构，带作用域的注册不会向下继承给 subagent，子树行为须靠 lineage 数据表达（glossary 行13）。
  • 限制工具不可见：被 restriction 过滤的工具与不存在的工具无法区分（glossary 行19）——模型侧无从分辨「被禁」与「没有」。
  • 恢复后默认停机：目标激活 armed/disarmed 有意不参与持久回放，恢复/fork 后须一次人类授权才开始自动工作（glossary 行27）——安全换来的是一次额外交互。
  • 持久保证依赖调用纪律：append 是 best-effort，只有 flush 是 durability barrier（persistence 行68-91）；冷恢复不继承 outputSchema（subagent 行132）。
